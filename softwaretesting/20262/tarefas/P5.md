**Projeto 05 \- Implantação de DevOps, Integração Contínua (CI) e Entrega/Implantação Contínua (CD) nos Projetos (Grupo)**

Para entregar as atividades de projeto, a equipe deve utilizar o repositório público oficial do projeto no GitHub e atualizar os links correspondentes neste repositório.

Nesta etapa final do projeto da disciplina, as equipes consolidarão as práticas da **cultura DevOps** integrando todos os níveis de testes automatizados e critérios de qualidade construídos ao longo do semestre (Unidade, Integração, Sistema/E2E e SonarQube) em uma **esteira automatizada completa de Integração Contínua (CI) e Entrega/Implantação Contínua (CD)**. O objetivo é assegurar que toda entrega de valor ao ambiente de execução seja protegida por testes de software que atuam como portões de qualidade (*Quality Gates*), aplicando os princípios de *Shift-Left Testing* (testes automatizados rápidos a cada Pull Request) e *Shift-Right Testing* (validação da saúde do sistema no ar via Smoke Tests).

---

### Passo a Passo da Atividade

#### Passo 1 — Organização e Fluxo Git/GitHub
1. O representante da equipe deve cadastrar uma **Issue** no repositório da disciplina (`bsi-tasks`) e no repositório do projeto com o título: `P5 - Implantação de DevOps, CI e CD no Projeto - Grupo <Nome>`.
2. Criar uma branch de desenvolvimento temática (ex.: `infra/#<id>-pipeline-ci-cd`).
3. Registrar commits utilizando o padrão **Conventional Commits** com referência explícita à issue (`#<id_issue>`).
4. Ao concluir, abrir um **Pull Request** para a branch principal (`main`), contendo a descrição das alterações, links das execuções de pipeline e evidências de publicação.

#### Passo 2 — Pipeline de Integração Contínua (CI)
A equipe pode escolher como motor de automação o **GitHub Actions** (recomendado) ou outra ferramenta livre/compatível (como GitLab CI):

1. **Gatilhos de Execução:** O pipeline de CI deve ser disparado automaticamente a cada **Push** e a cada abertura ou atualização de **Pull Request** direcionado à branch `main`.
2. **Estágios Obrigatórios de CI:**
   * **Setup e Lint:** Instalação das dependências com cache configurado e validação estática de código (linter / formatação);
   * **Testes de Unidade:** Execução automatizada da suíte de testes de unidade com isolamento de dependências externas por Mock Objects;
   * **Testes de Integração:** Execução automatizada dos testes de integração (validando regras com banco de dados de teste ou mocks de infraestrutura);
   * **Testes de Sistema (E2E Headless):** Execução automatizada em modo *headless* dos testes de sistema implementados na P3 (Selenium, Cypress, Playwright ou equivalente da stack do grupo);
   * **Métricas de Cobertura e SonarQube:** Geração dos relatórios de cobertura e envio das métricas para o servidor oficial do SonarQube do LABENS ([https://labens.dct.ufrn.br/sonarqube/](https://labens.dct.ufrn.br/sonarqube/)), utilizando token seguro via GitHub Secrets;
   * **Quality Gate:** A pipeline DEVE falhar de forma bloqueante se qualquer teste não passar ou se o Quality Gate do SonarQube for reprovado.

#### Passo 3 — Containerização da Aplicação
1. **Dockerfile:** Criar um `Dockerfile` de produção na raiz do projeto, utilizando boas práticas de segurança e otimização:
   * Construção em múltiplos estágios (*multi-stage build*), separando compilação/dependências do runtime final;
   * Execução da aplicação com usuário sem privilégios de root (*non-root user*);
   * Definição explícita de variáveis de ambiente padrão e porta de escuta.
2. **Docker Compose:** Criar ou atualizar o arquivo `docker-compose.yml` para orquestração dos serviços (aplicação, banco de dados PostgreSQL e eventuais serviços auxiliares), facilitando a replicação local pelos avaliadores.

#### Passo 4 — Pipeline de Entrega/Implantação Contínua (CD)
O estágio de CD deve ser acionado automaticamente apenas quando houver **merge ou push na branch `main`** (ou publicação de uma tag de versão SemVer `vX.Y.Z`) e **todos os testes do CI tiverem sido aprovados com sucesso**.

A equipe pode escolher **uma** das seguintes alternativas de ambiente para a publicação contínua:

* **Opção A — Ambiente da Disciplina / DCT:**
  * **Banco de Dados:** Servidor PostgreSQL 18 (`postgres18-server`);
  * **Execução:** Servidor com Docker para execução dos containers dos discentes;
  * **Roteamento:** Servidor Nginx atuando como proxy reverso para publicação provisória dos sistemas das equipes (com portas ou subdomínios alocados para cada grupo);
  * O pipeline de CD deve construir a imagem Docker, conectar ao `postgres18-server`, aplicar as **migrações de banco (*database migrations*)** automaticamente e subir o container atrás do proxy Nginx.
* **Opção B — Plataformas em Nuvem:**
  * Publicação contínua em plataformas com plano gratuito ou educacional (ex.: Render, Railway, Fly.io, Vercel ou similar) com banco PostgreSQL integrado e migrações automáticas.

**Gerenciamento Seguro de Credenciais:** Proibição estrita de credenciais no repositório. Uso obrigatório de **GitHub Secrets**.

#### Passo 5 — Testes de Fumaça Pós-Deploy (*Automated Smoke Testing*)
1. A equipe deve implementar um endpoint de checagem de integridade na aplicação (ex.: `/health` ou `/api/status`), validando que o servidor e o banco de dados PostgreSQL estão operacionais.
2. O pipeline de CD deve conter um step final automatizado de **Smoke Test**:
   * O pipeline realiza requisições HTTP automáticas contra a URL pública da aplicação publicada;
   * Valida se o status retornado é `200 OK`;
   * Se a aplicação não responder adequadamente após tolerância configurada (*timeout/retries*), o pipeline reporta falha de deploy.

#### Passo 6 — Documentação Técnica (`docs/relatorio-ci-cd.md`)
Elaborar relatório técnico no repositório do grupo contendo:
1. **Visão Geral e Arquitetura da Esteira:** Diagrama do pipeline (Mermaid) e descrição dos estágios;
2. **Cultura DevOps e Testes Contínuos:** Análise crítica sobre como o pipeline materializa os princípios de DevOps (eliminação de atritos, repetibilidade com Docker, Shift-Left e Shift-Right);
3. **Ambiente Escolhido:** Justificativa da escolha (Ambiente DCT com Postgres 18 + Docker + Nginx ou Plataforma em Nuvem) e descrição da infraestrutura;
4. **Instruções de Configuração:** Variáveis de ambiente necessárias e guia para rodar via Docker localmente;
5. **Links de Acesso:** URL pública da aplicação publicada, URL do endpoint de `/health`, link da execução do pipeline no GitHub Actions e link do projeto no SonarQube do LABENS;
6. **Evidências de Funcionamento:** Logs/screenshots da execução bem-sucedida, evidência do smoke test e badges no `README.md`.
